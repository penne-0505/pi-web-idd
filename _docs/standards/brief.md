# 依頼（計画役が実装役に渡す作業指示）

`plan.md` の中身の形を決める。計画役が書き、実装役と計画の査読が読む。`config/repos.yaml` の
`work_instruction: plan` を書いた repo だけが使う。文書の置き場・寿命は
`document_contracts.md` の plan の節を参照。触る場所・順序・確かめ方・やらないことを並べる旧い作業指示の形は、
この形に置き換えた。

## 計画役

計画役は、1 件の WorkItem を、実装役が人に聞き返さずに着手できる**依頼**に変える役である。

入力は Issue、Purpose、触る見込みの Place の Choice、原物。出力は「欄」の 6 欄を満たす依頼 1 通と、
依頼を書くために人に聞いた質問の記録。6 欄が埋まり、戻す条件まで書けたら終わりである。埋まらない欄は、
計画役が推測で埋める欄ではなく、人に聞く欄である。

計画役が責任を負うのは、依頼の**成立**である。実装の設計と結果には責任を負わない。設計は実装役が
原物と Choice から行い、結果は完了の形で判定される。

原物については所在・読み方・罠を書き、中身を要約しない。実装役の席から見えない事実を集め、
見える事実は書かない。how を書かず、理由を持って決めたことだけを「守ること + why」の形で残す。

## 欄

6 つ。この順で書く。各欄に、書くこと・書かないこと・入場条件を定める。

### 依頼

何をしてほしいか。1〜3 文。

- 活動（「会話の画面を作る」）ではなく、終わりの状態（「会話を送ると応答が返り、その会話を後から
  開いて続きを送れる」）で書く。活動は作れば達成になる。状態は確かめる手段を要求し、それが完了の
  形につながる。
- 正解が原物にあるなら、原物の所在をここに書く。「どこを見れば正解か」は依頼の一部。
- Issue の本文が原物なら、番号や URL だけでなく、実装役の席から本文を読む手段も書く。GitHub の
  Issue は `gh issue view <N> --repo <owner/name>` で読める。`gh` で読めない tracker は URL を書く。
  計画役の封筒の写し（state の `backlog.jsonl` の同じ lane の行の `context`）は本文の先頭 2000 文字
  だけで、lane の複製の外にもあるので、実装役の席から開ける所在として当てにしない。写しが本文の
  全体に届かないときは、実装役の席から開ける所在（読める URL か、本文を写した場所）を依頼に書き、
  それも無ければ戻す条件として人に返す。実装役の brief には Issue の URL しか届かず、本文は届かない。
  写しがあることは、依頼に所在を省く理由にならない。

### 意図

なぜ頼むのか。この lane の価値がどこにあるか。

- Purpose から引く。無ければ人に聞く。
- 出典（Issue、Purpose の id、人の回答）を持つ文だけを書く。計画役が自分で補った動機は、推測と
  明示するか、質問にする。この欄は捏造が最も起きやすい。
- 意図があると、実装役は書かれていない場面で局所の判断ができる。「見た目の忠実さに価値がある」と
  1 行あれば、prototype を開く理由を実装役が自分で持つ。
- **症状と原因を分けて書く**（`solving.md` の R1）。Issue が述べているのは症状のことが多く、症状だけを
  消す依頼は、迂回や橋渡しで満たされる。原因は、出典（原物を読んで確かめたこと）を持つか、推測と明示する。
  原因が Issue の範囲を越えるなら、依頼を書かずに止まり、Issue の立て直し（分ける・範囲を変える・別の
  Issue を先にする）を、あるべき形と理由つきで提案する（「Issue に押し返す道」）。欄は増やさず、この欄に書く。

### 重要なコンテクスト

知らないと間違った方向に進む事実。

- 入場条件は 3 つ全部: 事実であって指示でない。実装役の席からは見えない。知っていれば判断が変わる。
- 欄は lane のコンテクスト文書（`_docs/context/<Area>/<slug>/context.md`）の所在だけを指す。事実はその文書に書き、欄には写さない。同じ事実を 2 か所に置くと、計画役が直すのは片方だけになり、plan を読む段と文書を読む段で事実が食い違う。
- 文書の書き手は計画役だけではない。実装役は、実装中に知った同じ 3 条件の事実を、session の終わりにその文書へ追記して commit する。追記は書き換えでなく足すので、前の巡の事実が消えない。整理役と計画の査読もその文書を読む。blind・絵を見る役と判定には渡さない。
- 文書は lane の恒久の記録で、plan.md の archive に合わせて移さない。文書から `_docs/plan/` の plan.md を参照しない（plan は archive へ移る）。
- 入る: 既存の code が正でないこと。入力の性質と罠（1 行が 33,000 文字、`class` も `id` も無い、
  runtime が無いと描画されない）。環境の制約（道具の出力は末尾 50KB で切れる、画像を読めない
  model かもしれない、engine は他の lane と共用）。**計画役が自分で踏んだ回避**（「計画役はこの
  file を script で文字を削り出して読んだ」）。並走する lane との関係。実装役が自分で踏んだ回避も、
  追記として同じ形で入る。
- 入らない: 一般論、経緯、読めば分かること、やり方の助言。やり方に見えるもの（「整形してから読め」）は
  事実（「そのまま読むと先頭が落ちる」）に書き換える。手は実装役が選ぶ。
- 文書も膨らみやすい。入場条件を 1 つでも欠くものは入れない。

### 裁量

4 段で書く。禁止だけを書かない。

- **原理** 1 文。挙げていない場面に延びる言い方（「見た目は原物に従い、値だけ token にする」）。
  列挙は閉じて読まれる。
- **自由にしてよい。** 部品の分け方、file 構成、テストの形、原物を読みやすくする script を書く
  こと、など。agent は何も言われなければ既存を正として扱い、最小の変更に倒れる。この項が無いと
  骨組みで止まる。
- **触る範囲。** 触ってよい場所と、範囲外の隣接領域。思いつく限りを列挙しない。実装役が手を出し
  そうな所だけ。触る場所は backquote の path で始まる箇条書きか表で書く（本流の進みの読み取りが
  触る場所として拾う）。所有の範囲（`solving.md` の「所有か共有か」）では、これは柵ではなく、見込みと
  P2 の上限である。原因が範囲の外の持ち主の側にあるなら、実装役は範囲をその側へ広げてよく、広げたら
  報告に書く。共有の範囲では、範囲の外へ形を変えに出ず、提案にする。
- **守ること。** 破ると取り返しがつかないものだけ、各 1 行の why 付き。why があれば規則は原理に
  なり、書いていない同種の場面にも及ぶ。それ以外の「守ってほしいこと」は Place の Choice として
  届くので、ここに写さない。how に見えても計画役が理由を持って決めたこと（読み直しの順）は、
  手順ではなくこの形で書く。原則（`solving.md`）は P 番号で引き、本文を写さない（新しい形を入れたら
  同じ lane で旧い形を消す、なら「P4・R3」と引く）。

### 完了の形

**全体 1 文**と**床**に分ける。

- 全体: 列挙では満たせない、終わりの状態の 1 文。Purpose の want を lane の範囲で本物の状態に
  言い換えた文にする（「本物の engine につないだ画面で、利用者が会話を送り、その会話を後から
  開いて続きを送れる」）。成果物の性質（prototype と一致する・絵が同じ・無い）は全体に書かず、
  床か Choice に置く。「1 文」は状態が 1 つという意味で、文の数の規則ではない。判定者と判定の方法は、
  状態の文とは別の文で添えてよい。実装役以外が判定する。誰が判定するかは Harness が決める
  （人、絵を見る役、device_check）。実装役の自己申告で verified にしない。
- 全体の判定: 本物の状態（本物の engine と本物のデータ）の上で行う。偽の engine の画面と prototype と
  並べた絵は床の確かめに使ってよいが、全体の判定の代わりにしない。同じ結果を何度でも出せるので、
  偽 engine と絵は床の確かめに向く。
- 床: 3〜6 項目。状態の記述で、どれだけ具体的でもよい。ただしテストを見れば自明なこと（断り方の
  文言、終了コード、JSON の欄、冪等の確かめ方）は書かない。床は AC として展開されるので、
  `work.md` の「受け入れ条件（AC）」の 3 つの条件を満たす文で書く。床が 10 を超えるなら責務が複数混ざっている
  （`_docs/standards/granularity.md`）。
- 判定の問い: **別の作り方をした 2 つの実装が、両方これを満たせるか。** 満たせるなら状態。
  1 つの作り方しか満たせないなら how で、ここに書かない（仕組みを揃える理由があるなら
  「守ること + why」へ）。
- 具体の列挙だけで全体を欠くと、列挙は天井になる。「画像が残っている」は満たして止まる。
- acceptance（`work.md` の AC）は床から展開する。計画役は床に無い AC を足して表を膨らませない。今は計画役が
  qa.md に書き、Harness が床から機械で展開する形は未実装である。

### 戻す条件

実装役が止まって人（か計画役）に返す条件と、返し方。

- Purpose を決められない分岐（`workflow.md` の「Purpose を決められない問いは人へ」）。
- **入力・手段の不足。** 原物が開けない・撮れない・読めない。完了の形を確かめる手段が自分の道具に
  無い（画像を読めない、端末が無い）。回避せず止まる。回避したなら、その事実を記録に残す。
- 裁量の境界を越えないと成立しない箇所が出た。
- 時間。予算の中で全体に届かない見込みが立ったとき、どこを削るかを聞く。
- 返し方も書く。「撮るところまでやって、見ていないと書いて戻す」。見ていないものを見たと書かない。

## 実装役

実装役は、依頼の裁量に従い、`solving.md` の原則を P 番号で引いて実装する。

- 課題は原因で解く（P1）。症状だけを消す迂回や、旧い形と新しい形を共存させるためだけのもの（橋渡し）を
  足さない。
- 新しい形を入れたら、同じ lane で旧い形を消す（R3）。消せないなら、応急処置として Choice に記録する
  （P7・R9。`records.md` の「旧い形を残す変更」）。応急処置を原因による解決と書かない。
- 完了の報告は、残した旧い形と互換の分岐が、記録された応急処置か宣言された契約を守る互換かを AC と evidence で示す（R5。`work.md`）。
- 原因が依頼の範囲を越えると分かったら、実装を続けず、戻す条件に従って返す。

## 書かないもの

- 順序、手順、関数の分割、テストの構成。実装役が導ける。
- 原物の要約。所在と読み方を書く。
- 出典や経緯を本文に混ぜること。
- AC の表、Choice（旧い形の lane では DEC）の一覧の写し。記録を指す。

長さの目安は 40〜60 行。超えたら削るのではなく、どの欄に入場条件を欠くものが入ったかを疑う。

## 計画の査読が見るもの

設計の正しさではなく、**依頼として成立しているか**。次の 6 観点で読む。

1. 原物があるとき、その所在と読み方があるか。要約で代えていないか。
2. 意図に出典があるか。計画役の補いが推測と明示されているか。
3. 完了の形に全体 1 文があり、判定者が実装役以外か。全体 1 文が成果物の性質でないか。床は状態の
   記述か。
4. 守ることに why があるか。取り返しがつかないものに絞られているか。
5. 戻す条件に入力・手段の不足があるか。
6. how（順序・手順・関数の分割・テストの構成）が混ざっていないか。

加えて、`solving.md` の P1・P7 に照らして読む。症状だけで原因の無い意図と、迂回や橋渡しで課題を満たす
依頼（旧い形を残す依頼で、応急処置の Choice の草案が無いものを含む）は、実装役が補えない欠けなので must にして
計画役へ差し戻す。

成立しない欠け（原物があるときの所在・全体 1 文と判定者・戻す条件の手段の不足・意図の出典）は must にして
計画役へ差し戻す。全体 1 文が成果物の性質であるときも must にする。v2 の lane では、その lane が
出した Purpose の案の want が成果物の性質であるときも must にする。草案が連なる既存の active な
Purpose の want が成果物の性質であるときは should にする（planner には差し戻さず、GO の人に
見える）。how の混入と why の無い守ることは should にする。

## 深さとの関係

`workflow.md` の深さの表は変えない。案（未実装）: 正解が原物にある task（移植、写し、変換、既存の形への
追従）は、計画役の価値が小さい。浅い lane では、依頼の 6 欄が Issue と原物だけで埋まるなら計画役を飛ばして
実装役に直接渡してよい（短い指示と原物の dir だけで忠実な移植が出た実験がある）。

## Harness 側で持つもの

- 全体 1 文の判定者の割り当て（device_check の宣言、絵を見る役）。
- 「手段が無い」の機械の検出（道具の返事の `does not support images` など → 場所に付いた指摘）。
- 実装役の role policy「変更は最小」の扱い。
