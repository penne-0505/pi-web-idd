# 課題解決の原則

課題を解くときの原則と、それを各役に効かせる規則を置く。計画役・計画の査読・実装役・差分のレビュー役・判定は、この文書の番号を根拠に引き、本文を自分の規範や依頼文に写さない。写しは改訂で食い違い、agent は読んだ方に従うためである。

原則の番号は `P1`〜`P7`（ハイフン無し）で、Purpose の id `P-<n>`（`records.md`）とは別である。規則の番号 `R<n>` は本書の規則で、`workflow.md` が外した旧い R2（守られたかの確かめ）とは別である。番号は消さず、規則を足すときは番号を足す。

## 解く問題

coding agent は「何も壊さずに課題をとりあえず満たす」ことに倒れ、持ち主の口を広げずに手元で作るか推し量る変更（橋渡し・迂回・互換の分岐）を積む。測れる終端が「既存のテストが通ること」しかなく、壊すことには罰があり、借りを残すことには罰が無いためである。借りが積み重なると、変更のたびに前の借りをほどく仕事が増え、後から直す人も agent も原因を見失う。

## 原則

規則はこの番号を根拠として引く。規則が場面に合わないときは原則に戻って判断する。

- **P1. 課題は原因で解く。** 望ましい変更は、課題をその場で満たすものではなく、系が特別扱いなしにその課題を満たす形へ直すものである。
- **P2. 変更の大きさは、課題の構造的な原因に比例させる。** 小さくすべきは差分ではなく、系の形の変更である。小さな課題のために周辺を作り直さない。
- **P3. 途中の不整合は道のりの一部であり、避けない。** より良い形へ移る途中で内部の経路・型・テストが一時的に合わなくなるのは、直すことの一部である。許されるのは lane の branch の中だけで、本流に取り込む時点では内部は整合している（取り込みの検査がこれを確かめる）。
- **P4. 変更は、内部が再び整合し、記録の無い橋渡しが残っていない時点で完了とする。** テストが通ることは必要条件であって十分条件ではない。残してよい旧い形は、P7 の記録された応急処置と、P5 の宣言された契約を守る互換だけである。
- **P5. 守るのは契約と不変条件である。内部の形は守る対象ではない。** 後方互換は契約に対してだけ価値を持つ。
- **P6. 形を直せる範囲は、propter が代行する人の設計意図が及ぶ範囲である。** 所有の範囲では原因で解く。共有の範囲では局所の慣習に合う変更だけを行い、形の変更が要るなら実装せず、あるべき形と理由を提案する。提案が合意されたら（Choice になったら）、その形において所有の範囲に移る。
- **P7. 応急処置は、応急処置と明記して行う。** 選んでよい。ただし、応急処置であること・本来の直し方・今そうしない理由を記録し、本来の直し方を後続として起こす。応急処置を原因による解決と言い換えない。

P1 が中心である。P2 は作り直しの暴走を抑え、P3・P4 は「途中で合わなくなってよいが、取り込む時には揃える」を定める。P5 は何を失ってはならないか、P6 はどこで P1 を使ってよいかを定め、P7 は P1 からの逃げ道を隠さずに正規化する。

## 語

| 語 | 定義 | propter での当て方 |
| --- | --- | --- |
| 変更単位（整合の単位） | 本流に取り込まれる最小のまとまり | lane。branch の中は不整合を許し、取り込みの検査が境目の整合を確かめる |
| 課題の単位 | 何を解くかの単位 | Issue。Issue の立て方そのものが症状の水準のことがある（「Issue に押し返す道」） |
| 契約 | 変更の外の誰か・何かが依存している振る舞いや形式 | repo ごとに `config/repos.yaml` の `contracts` に一覧で宣言する（「契約」） |
| 不変条件 | 系がどの状態でも満たし続けるべき性質 | 台帳は追記だけ、署名した中身だけが外へ出る、など。Choice の anchored と規範が持つ |
| 内部の形 | 契約でも不変条件でもない構造の選択 | 呼び出し経路、内部の型・関数、module の分け方、既存のテストの書き方。同じ commit から作られる engine と画面の間の API もここ |
| 橋渡し | 旧い形と新しい形を共存させるためだけのもの | 互換の分岐、新旧の切替、重複した経路、迂回、「とりあえず」の特別扱い。台帳の古い記録を読む分岐は契約側（P5）で、橋渡しではない |
| 応急処置 | 今は契約を満たすが、原因が残る変更 | 橋渡しを残す変更と、症状だけを消す変更。P7 に従い Choice で記録する |
| 形の判断主体 | その範囲がどういう形であるべきかを決める人 | 変更の権限とは別。「所有か共有か」で持つ |
| 合意された形 | 共有の範囲で提案が合意されたもの | Choice（anchored）として台帳に残す |

## Issue に押し返す道

整合の単位（lane）と課題の単位（Issue）は分ける。Issue の立て方が症状の水準で、原因が Issue の外にあるときは、lane の中では解けない。

1. **計画の段**: 計画役は症状と原因を分けて書く（R1）。原因が Issue の範囲を越えるなら、実装に入らずに止まり、Issue の立て直し（分ける・範囲を変える・別の Issue を先にする）を、あるべき形と理由つきで提案する。
2. **実装の途中**: 形の誤りが分かったら、計画から考え直す判断に回す（判断の役は別の lane が持つ）。必要なら Issue の作り直しまで提案する。
3. **今すぐ立て直せないとき**: P7 の応急処置として Choice に記録して進め、原因の側を後続の Issue の案にする（R9）。

## 契約

契約は repo ごとの事実で、`config/repos.yaml` の repo の `contracts` に 1 か所で並べる。

- 宣言の無いものは内部の形として扱う。
- 永続データの形式と公開の interface は、宣言が無くても契約として扱う。
- 契約を変える変更は、P5 の対象であり、互換を保つか、契約の側を直す計画を要する。
- 機械の読み口と、契約を確かめるテストの印（R4）は、契約の一覧が定まってから足す。

propter（pi-web-idd）の一覧は `config/repos.yaml` にある。engine と画面の間の API は内部の形とし、そのために画面の bundle は engine と同じ commit から作ったものだけを配る（版のずれを許さない。配り方は別の lane が持つ）。

## 所有か共有か

「どの範囲で形を直してよいか」は誰のために動くかで変わる（P6）ので、repo の事実（`repos.yaml`）ではなく人の側の設定に置く。

- 共有の範囲は人が明示した範囲に限る。宣言が無い範囲は所有として扱い、原因で解く。
- 共有の範囲では局所の慣習（同じ module・同じ層の隣の code が採っている形）に合わせる。局所の慣習で解けない、または慣習に沿うと橋渡しが要るときだけ、実装せずに提案する。
- 人の側の設定の器は未実装である。器ができるまで、共有の範囲を宣言する経路は無く、すべての範囲を所有として扱う。共有の範囲に関する規則（R6〜R8）は、共有の repo で lane を回すときに入れる。

## 規則と効く場所

| # | 規則 | 根拠 | 効く場所 |
| --- | --- | --- | --- |
| R1 | 計画に、課題の症状と原因を分けて書く。原因が Issue を越えるなら止まって立て直しを提案する（「Issue に押し返す道」） | P1・P6 | `brief.md` の意図の欄。計画の査読が、原因の無い計画と、迂回で課題を満たす計画を must で戻す |
| R3 | 新しい形を入れたら、同じ lane で旧い形を消す。残すなら P7 の応急処置として記録する | P4 | `brief.md` の実装役の守ること。差分のレビューと判定が、旧い経路の残りを指摘の理由にできる |
| R5 | 完了の報告に、残した旧い形と互換の分岐を列挙し、一つひとつが記録された応急処置（P7）か、宣言された契約を守る互換（P5）かを示す。どちらでもないものが残っていれば完了ではない | P4・P5・P7 | `work.md` の AC と evidence。報告の欄は足さず、AC の evidence で示す |
| R9 | 応急処置は Choice に記録する（応急処置であること・残す範囲・本来の直し方・今しない理由）。本来の直し方は後続の Issue の案として起こす | P7 | `records.md` の「旧い形を残す変更」。判定が、記録の無い応急処置を差し戻す |
| R10 | lane はレビューできる大きさに保つ。原因による解決が 1 つの lane に収まらないなら、各段が整合するよう分ける | P2・P3 | `granularity.md`（計画の段の粒度）。判断の役 |
| R11 | 変更の範囲が原因を超えていないかを示す。所有の範囲では、原因に届くのに必要な分だけ計画の範囲を広げてよく、広げた場所と理由を報告に書く | P1・P2 | 巡ごとの行（計画の範囲の外の file）で測る。測定は別の lane が持つ |

- R1 と R3 は計画と差分の読み手が差し戻す規則である。差し戻されなければ原則は読まれるだけになるので、読み手の依頼文は P 番号で理由を引く（`checks.md`）。
- 後に入れる規則は R12（橋渡しの機械判定。構造の宣言に橋渡しの数を足し、数え方を決めてから）、R4（契約を確かめるテストの印）、R6〜R8（共有の範囲で契約を変えない・局所の慣習に合わせる・形を変えるなら提案する）。

## 応急処置の記録

旧い形を残す変更は、Choice として記録する（`records.md` の「旧い形を残す変更」）。

- chosen は、残す形の名詞句にする。応急処置を原因による解決と呼ばない。
- 残す範囲は place と anchored に、本来の直し方は rejected（本来の形とその形を今取らない理由）と revisit に、今そうしない理由は why に書く。
- revisit は後続の Issue を指し、その Issue が閉じたときに応急処置の Choice を置き換える。
- 後続の Issue は `idd out draft --kind gh-issue` で案として起こす。投稿は人が承認したときだけ起きる（P-2）。役は投稿しない。
- コードのコメントには書かない（`records.md` の「コードとの結び付き」）。

## 未決

- 「原因」の判定の強化。橋渡しを足さずに症状だけ消す変更（例外の握りつぶしなど）をどう見つけるか。今は差分のレビューと判定の観点で持つ。
- 応急処置の返済。起こした後続を誰がいつ回収するか。応急処置の数を構造の指標に入れて見える化するか。
- 導入直後は「作り直しの暴走」（P2・R10・R11 の違反）が増えうるので、しばらくはそちらを重点的に見る。
